## 2. 決策與建議

### 2.1 OAuth 發布狀態：改成「正式版」，不送驗證 ✅

| 選項 | 結果 | 建議 |
|---|---|---|
| 測試（Testing） | 只有清單內帳號可登入（上限 100）；**每 7 天必須重新登入**，活動期間會一再中斷 | ✗ |
| **正式版、未驗證** | 任何帳號可登入；第一次會看到「Google 尚未驗證這個應用程式」，按「進階 → 前往（不安全）」；登入長期有效；未驗證 app 累計最多 100 位使用者 | **✓ 建議** |
| 正式版、送驗證 | 需首頁、隱私權政策、網域驗證、示範影片；敏感範圍驗證免費，但審核時間通常以週計，**10/21 前很可能來不及**，而且使用者只有幾位，效益很低 | ✗ |
| 內部（Internal） | 只有在 Cloud 專案屬於某個 Google Workspace 組織、且所有管理者都是該組織帳號時才能選；不會有未驗證警告 | 只在上述條件成立時考慮 |

> 注意：若目前是「測試」狀態，改成正式版之後，**之前發的 token 仍會在 7 天內到期**，每台電腦要重新登入一次（設定 → 重新連線）。之後就長期有效。

### 2.2 用哪個 Google 帳號登入：專用帳號 ✅

`spreadsheets` 範圍在 Google 端能讀寫該帳號看得到的**所有**試算表（程式本身只操作設定的那一份）。建議：

- 建一個專用 Gmail（例如「報名後台」用途），**只**把正式回應試算表以「編輯者」分享給它，程式用它登入。
- 不建議用學校 Workspace 帳號（`gs.ncku.edu.tw` 等）：組織管理員可能封鎖未驗證的第三方 app（Phase 0 決策 #12 仍「待確認」），臨時被擋會很難處理。
- 若一定要用學校帳號，請先用測試試算表實際登入一次確認沒被擋。

### 2.3 程式碼簽章：不買 ✅

- 使用者只有少數已知的管理者，第一次安裝時 SmartScreen 會出現「Windows 已保護您的電腦」，按「其他資訊 → 仍要執行」即可；之後的自動更新不會再跳。
- 簽章的成本：OV 憑證約每年 US$200–500，現在須搭配硬體金鑰或雲端 HSM，申請需數天到數週；微軟的雲端簽章服務（Artifact Signing，原 Trusted Signing）約每月 US$10，但申請資格有限制。對這次活動不划算。
- 若之後要長期、多人使用，再在 `publish.ps1` 的 `vpk pack` 加 `--signParams`。

### 2.4 誰安裝、怎麼安裝

- **主要管理者電腦 1 台**：日常審核、核帳、匯出都在這台。
- **備援 1 台**（可用你自己的開發電腦）：只在主要電腦故障時使用；平常**不要**同時修改。
- 安裝方式：把 GitHub Releases 頁面上的 `RegistrationAdminApp-win-Setup.exe` 下載連結傳給管理者，雙擊安裝（不需系統管理員權限），之後自動更新。
- 公開 Release 內含 OAuth 用戶端檔。Google 視電腦版 client secret 為非機密，單獨拿到它無法讀任何資料；風險只是別人可能用你的 app 名稱發起登入、占用 100 人額度。可接受；若在意，活動結束後到 Cloud Console 刪除該 OAuth 用戶端即可。

### 2.5 切換到正式回應試算表：10/14 前完成 ✅

理由：保留一週處理意外（欄位標題不同、權限、登入被擋），截止前後是最忙的時段，不應在那時才切換。

程式在正式試算表會**新增 5 張管理分頁**，原始回應工作表不會被改動，Google 表單照常寫入。但能開這份試算表的其他人都會看到這些分頁（`_Admin` 含審核備註），所以要先確認共用名單。

| 每個審核日結束 | 程式「匯出」XLSX 一份，存到加密或只有自己能開的資料夾 | 主要管理者 |

## 3. 執行步驟

### 步驟 A：Google Cloud Console（你自己操作，約 5 分鐘）

1. 開啟 <https://console.cloud.google.com/>，左上角選專案 **registrationmanage**。
2. 左側「API 和服務 → OAuth 同意畫面」（新版介面叫「Google Auth Platform」）。
3. 看「發布狀態」：
   - 若是「測試中」：按「**發布應用程式**」→ 確認。不要按「準備驗證」或上傳任何驗證資料。
   - 若已是「正式版」：不用動。
4. 「品牌（Branding）」頁確認應用程式名稱是中性的（例如「活動報名後台」）、使用者支援 Email 是你看得到的信箱。
5. 「資料存取（Data access）」頁確認登入範圍為 Sheets、openid、email，選擇器範圍為 `drive.file`；不要求 `drive` 或 `drive.readonly`。
6. 「API 和服務 → 已啟用的 API」確認 **Google Sheets API**、**Google Picker API** 與 **Google Drive API** 已啟用。
7. 用測試試算表在你的電腦按「設定 → 重新連線」登入一次，確認會看到「未驗證」頁並能繼續進入。

### 步驟 B：專用帳號與共用（你／試算表擁有者）

1. 建立專用 Gmail（或決定沿用哪個帳號，見 2.2）。
2. 試算表擁有者打開**正式**回應試算表 → 共用 → 加入該帳號為「編輯者」。
3. 檢查共用名單：只留必要的人；告知他們不要編輯 `_` 開頭的分頁、不要在回應頁排序或改標題。

### 步驟 C：切換前檢查（我可以協助，不碰正式試算表）

1. 比對正式回應工作表的第一列標題與測試試算表的第一列是否完全相同（測試表若是從正式表複製的，通常一致）。可以把兩邊第一列貼給我比對。
2. 確認 `_Config` 要用的值：名額 20、報名截止的**時間**（目前只有日期）。

### 步驟 D：正式切換（主要管理者電腦，約 10 分鐘）

1. 試算表擁有者先完成 2.6 的「切換前備份」。
2. 安裝程式（第一次會有 SmartScreen：「其他資訊 → 仍要執行」）。
3. 開啟程式 → 設定 → 貼上**正式**試算表網址 → 「檢查連線」→ 瀏覽器用專用帳號登入 →「進階 → 前往（不安全）」→ 允許。
4. 只有一張回應工作表時程式會直接詢問「建立管理資料區」，確認即可；若有多張，到「進階（管理員）」選原始回應工作表再建立。
5. 到「進階」看欄位檢查：不應有缺少或對不上的欄位。
6. 核對：名單總筆數＝ Google 表單「回覆」分頁的回覆數。
7. 到試算表 `_Config` 確認 `capacity`＝20、`registration_close_at` 填上正確日期時間。
8. 先挑 1 筆真實報名只做「查看」，不要修改；確認資料正確後才開始正式審核。

### 步驟 E：上線後

- **更新凍結**：10/14–10/21 期間只發修正錯誤的版本，不加新功能；每次發版先用測試試算表驗證（`dotnet test` ＋ UAT 工具只對測試表）。
- 你的開發電腦之後若要測試，請在設定中改回**測試**試算表，用完再改回；不要讓兩台電腦同時對正式表修改。
- 出問題時：「設定 → 匯出診斷資料」（已遮蔽個資）傳給維護人員。

### 步驟 F：活動結束後

1. 最終備份（2.6）。
2. 各電腦「設定 → 登出」（刪除本機 token），再到「應用程式」解除安裝；要讓所有電腦的授權一次失效，到登入帳號的 Google 帳戶 →「安全性 → 第三方應用程式與服務」移除「活動報名後台」。
3. 從試算表共用名單移除專用帳號；刪除不再需要的匯出檔。
4. 若不再使用：Cloud Console 刪除 OAuth 用戶端或整個專案。

## 7. 之後的方向：把報名後台做大，並保留整合成內部系統的路

> 背景（2026-10-05 你的構想）：之後還要做會計系統，希望整合成一個內部系統，依登入身分使用不同功能。目前先把報名後台做大做廣，會計系統這次不做。

### 7.1 先講結論

**10/21 前不動架構，只做上線。活動結束後，下一個大步驟是加一個「後端伺服器＋資料庫」，報名後台當第一個模組搬上去；會計系統之後當第二個模組。** 理由在 7.2。

### 7.2 為什麼現在的架構撐不到「多系統、依身分分權限」

| 限制 | 對報名後台的影響 | 對整合內部系統（含會計）的影響 |
|---|---|---|
| 資料存在 Google 試算表 | 單一活動、少量資料可行 | 會計需要交易一致性、不可竄改的帳；試算表沒有交易、沒有原子寫入，只能「一位主要編輯者」 |
| 權限由「試算表共用」決定 | 有編輯權的人在 Google 端可以直接改任何分頁 | **無法依身分分權限**：桌面程式擋得住畫面，擋不住使用者直接開試算表；權限必須在伺服器端強制 |
| 每位使用者自己做 Sheets OAuth | 每人都會看到「未驗證」頁，最多 100 人 | 人越多越麻煩；改成伺服器代為存取後，使用者只需「用 Google 帳號登入」（只要 `openid`、`email`，非敏感範圍，不會有未驗證警告） |
| 每台電腦安裝桌面程式 | 少數管理者可接受 | 多部門、多身分時，網頁版免安裝、集中更新與權限較好管 |

### 7.3 現在就該維持的設計（成本很低，之後少走冤枉路）

1. **商業規則留在 `RegistrationAdmin.Core`，不寫進畫面。** 目前狀態轉換、名額、問題偵測都在 Core，且不依賴 WPF 或 Google。之後的伺服器（ASP.NET Core）可以直接重用這一層。新功能照這個原則做。
2. **資料存取只經過 `IRegistrationStore`。** 目前只有 Google Sheets 這一個實作；之後加「資料庫實作」即可替換，畫面與規則不必重寫。不要讓新功能繞過它直接呼叫 Sheets API。
3. **報名編號是對外的穩定鍵。** 會計之後的「應收／收款」要以報名編號對到報名紀錄，所以報名編號規則（`_Config.registration_no_prefix`）上線後不要再改。
4. **付款資料要能匯出成「一筆一筆的收款紀錄」。** 現在 `_Admin` 每筆報名只有一組付款欄位（應付金額、匯款人、帳號末五碼、入帳時間、核帳時間）。這次活動夠用；會計系統上線時，再把它轉成獨立的收款紀錄（一筆報名可對多筆收款／退款），由會計模組管理。
5. **異動紀錄（`_ChangeLog`）持續寫。** 之後搬到資料庫時，這就是稽核軌跡，會計一定需要。
6. **Google 表單繼續當報名入口。** 不論後端怎麼換，表單→回應試算表→同步進系統這條路都可以保留，報名者不受影響。

### 7.4 報名後台「做大做廣」的功能（依建議順序）

| 順序 | 功能 | 說明 | 是否需改架構 |
|---|---|---|---|
| 1 | 多活動 | 程式記住多份試算表，可切換活動；每個活動一份回應試算表 | 否 |
| 2 | 銀行入帳對帳 | 匯入銀行或郵局的入帳明細（CSV），依金額＋末五碼＋日期自動配對、人工確認 | 否；也是會計模組的前身 |
| 3 | 通知信 | 產生「通過待付款／已確認／候補」的收件人清單與信件內容（先用匯出＋合併列印，不讓程式直接寄信，避免再加 Gmail 權限） | 否 |
| 4 | 報到 | 活動當天依報名編號或 QR Code 報到，記錄出席；三日全勤統計 | 否 |
| 5 | 證書／收據 | 依出席與付款狀態批次產生 PDF | 否 |
| 6 | 統計與歷年報表 | 跨活動統計報名、付款、出席 | 多活動完成後即可 |
| 7 | 多人同時處理 | 需要真正的鎖定與交易 | **是**，等後端（7.5） |
| 8 | 依身分分權限、會計模組 | 見 7.5 | **是** |

1–6 可以在現在的桌面程式裡做；7、8 需要後端。

### 7.5 內部系統的目標架構（之後再做，現在只先確定方向）

```
報名者 ── Google 表單 ── 回應試算表
                              │（伺服器定時同步）
                              ▼
             ┌──────────────────────────────┐
             │  後端（ASP.NET Core）          │
             │  - 重用 RegistrationAdmin.Core │
             │  - 身分與角色（報名管理／會計／ │
             │    管理員），權限在這裡強制     │
             │  - 異動紀錄、備份               │
             │  資料庫（PostgreSQL）           │
             └──────────────────────────────┘
                              │
               網頁介面（建議）或現有 WPF 程式
                 依登入身分顯示：報名｜會計｜…
```

- **登入**：用 Google 帳號登入（只要 `openid`、`email`），系統內自己維護「誰是什麼角色」。
- **試算表存取**：改由伺服器用一個專用帳號或服務帳戶讀取，使用者不再需要 Sheets 權限。
- **介面**：建議改成網頁版（例如 Blazor，可沿用 C#），免安裝、權限集中；若想保留桌面程式，WPF 也可以改成呼叫後端 API。這個選擇可以等會計需求明確時再決定。
- **費用（估計）**：小型雲端主機＋資料庫約每月 US$5–25；若學校或組織有可用的伺服器可為 0。報名與會計資料都是個資／財務資料，主機位置、備份與存取權限要先跟負責單位確認。
- **搬遷順序**：先建後端與資料庫 → 報名模組改用資料庫實作的 `IRegistrationStore` → 把歷次活動的 `_Admin`／`_ChangeLog` 匯入 → 加角色 → 再開始會計模組。

## 8. 多人使用的詳細做法（2026-10-05 補充）

> 情境：程式要交給其他人（主要管理者）日常使用，你自己也會開來看。OAuth 用戶端已換成 Cloud 專案 `internalsystem-510706`，安裝程式 v0.2.1 起內含新用戶端。

### 8.1 角色與分工

| 角色 | 人數 | 做什麼 | 不做什麼 |
|---|---|---|---|
| 主要管理者 | 1 | 審核、會員核對、付款核帳、發票、匯出每日備份 | — |
| 你（維護者／查看者） | 1 | 查看進度與數字、處理問題、發新版 | 主要管理者在操作時不按「儲存」 |
| 備援 | 0–1 | 主要管理者請假或電腦故障時接手 | 平常不修改 |
| 試算表擁有者 | 1 | 共用設定、切換前與截止後建立副本 | 不在回應頁排序、改標題或改答案 |

**一次只能有一個人在改資料。** 程式用 row_version 偵測衝突：兩台電腦改同一筆時，後儲存的那一台會看到「雲端資料在您載入後已被修改」，資料不會被覆蓋，重新整理後再改即可。但這只是保護網，不是讓多人同時作業的機制。

### 8.2 Google 帳號：共用一個，或每人各自一個

兩種都可以，程式都支援：

| | 共用一個專用帳號 | 每人用自己的帳號 |
|---|---|---|
| 設定 | 試算表只分享給這一個帳號（編輯者） | 試算表分別分享給每個人（編輯者） |
| 多台電腦 | ✅ 可以。每台電腦各自登入一次，登入資料各自加密存在該電腦，互不影響 | ✅ |
| 某人離開時 | 要改密碼，所有電腦都要重新登入 | 從共用名單移除那個人即可 |
| 誰改了什麼 | 試算表「版本記錄」只看得到同一個帳號 | 「版本記錄」看得到是誰 |
| 密碼與兩步驟驗證 | 要分享密碼；兩步驟驗證的手機只有一支，別人登入時要找你按確認；從不同地點登入，Google 偶爾會要求額外驗證 | 不用分享密碼 |
| 「未驗證」提示 | 每台電腦第一次登入各看一次 | 每人第一次各看一次 |

**建議：** 人少（2–3 人）而且都是你信得過的人，共用一個專用帳號最簡單；只要有一個人不是長期合作，就改用各自帳號。不要用個人主要的 Gmail 或學校帳號當共用帳號。

共用帳號的注意事項：
- 0.2.2 之前的版本按「登出」會向 Google 撤銷授權，**會讓其他電腦一起被登出**；0.2.2 起只登出這台電腦。若在 0.2.1 上按了登出，其他電腦重新登入一次即可。
- 同一帳號、同一用戶端最多同時保有約 100 組登入，幾台電腦不會有問題。
- 要一次讓所有電腦失效：Google 帳戶 →「安全性 → 第三方應用程式與服務」→ 移除「活動報名後台」，或改密碼。

### 8.3 給主要管理者：安裝與第一次設定（約 10 分鐘）

1. 傳給對方：
   - 安裝程式連結：<https://github.com/lemongrasses/RegistrationAdmin-releases/releases/latest/download/RegistrationAdminApp-win-Setup.exe>
   - 正式回應試算表網址
   - 登入用的帳號（共用帳號時另以安全方式給密碼，不要和網址放在同一則訊息）
   - 操作說明：本機 `docs\操作說明.md`（或 `docs\manual`），可轉成 PDF 給對方
2. 對方雙擊安裝程式。出現「Windows 已保護您的電腦」→「其他資訊」→「仍要執行」（未簽章的正常提示，只有第一次）。不需要系統管理員權限。
3. 開啟程式 →「設定」→ 貼上正式試算表網址 → 登入 Google。出現「Google 尚未驗證這個應用程式」→「進階」→「前往（不安全）」→「允許」。
4. 正式試算表已由你建立好管理分頁時，程式會直接載入名單，不會再問建立分頁。
5. 確認名單總數＝Google 表單「回覆」頁的回覆數。
6. 之後開程式會自動登入、自動檢查更新，不用再設定。

建議第一次用視訊陪同，並先讓對方用**測試試算表**練習一輪（審核→待付款→核帳→已確認、匯出），練完再改回正式網址。

### 8.4 主要管理者的每日流程

1. 開程式（自動重新整理），或按「重新整理」（F5）。
2. 「總覽」看新報名、待確認、名額、資料問題。
3. 新報名：核對會員 → 資格 → 「通過待付款」或「候補」／「不通過」（填理由）→ 儲存（Ctrl+S）。
4. 收到匯款：填匯款人、末五碼、付款日、核帳日 → 付款狀態「已核帳」→ 報名狀態「已確認」→ 儲存。
5. 「問題清單」處理缺漏、重複、統編警告：確認後「接受例外」並寫原因。
6. 下班前：「匯出 XLSX（全部報名）」存一份到只有自己能開的資料夾（每日備份）。
7. 名額滿時新報名只能保持審核中或轉候補；有人取消後，從候補第 1 位開始遞補。

### 8.5 你自己查看時

- 安裝同一個程式（或用開發版），設定同一份正式試算表網址、用你能存取的帳號登入。
- 開啟前先問主要管理者是否正在操作；查看時只看、按重新整理，**不要按「儲存」、不要套用狀態**。
- 只想看數字或名單，也可以直接開 Google 試算表看 `_Admin`，或請主要管理者傳匯出檔；這兩種完全不會干擾對方。
- 你的開發電腦要測試新版時，先把設定改回**測試試算表**，測完再改回正式；測試工具（UatHarness、整合測試）**永遠只對測試試算表**。
- 若之後需要，可加一個「唯讀模式」開關（查看者無法儲存），屬小改動，可在需要時再做。

### 8.6 更新怎麼發

- 我改好程式 → 用測試試算表跑測試 → `scripts\publish.ps1` 發到 GitHub Releases（版本號遞增）。
- 已安裝的電腦**下次開程式**時自動下載、重新開啟後套用；不會動到設定與登入資料（存在 `%LOCALAPPDATA%\RegistrationAdmin`）。
- 10/14–10/21 更新凍結：只發修正錯誤的版本，並先通知主要管理者。

### 8.7 常見狀況

| 狀況 | 處理 |
|---|---|
| 登入後說「Google 回應 403」 | 該帳號沒有試算表編輯權限 → 試算表擁有者分享「編輯者」 |
| 登入頁顯示「存取遭封鎖」或「此應用程式已遭封鎖」 | 學校／公司帳號被組織政策擋 → 改用一般 Gmail；或 OAuth 同意畫面仍是「測試」且帳號不在測試使用者名單 → 發布為正式版 |
| 每 7 天要重新登入 | 同意畫面仍是「測試」→ 改「正式版」 |
| 儲存時出現「雲端資料在您載入後已被修改」 | 有別人（或另一台電腦）剛改過 → 按重新整理再改；你的輸入不會寫入，請重打 |
| 「Google API 配額暫時用盡」 | 程式已自動重試約 90 秒；等 1 分鐘再按儲存，輸入仍在畫面上 |
| 「來源欄位檢查未通過」 | 有人改了 Google 表單題目或回應頁標題 → 找維護者（你）調 `_FieldMap` |
| 新電腦、重灌或換 Windows 帳號 | 重新安裝、重新登入即可；資料都在試算表 |
